# 讓使用者快速理解開發中的 repository

研究日期：2026-09-07。狀態：原始研究提案已實作為 [explain-project](../skills/explain-project/SKILL.md)；隔離範例的評估見[執行紀錄](../evaluations/explain-project/runs/2026-09-07/README.md)，尚未在真實產品 repo 上評估效果。

## 結論

建議獨立成為 `explain-project`：讀取目前 checkout 的實作，先用使用者的語言說清楚產品做什麼、各部分負責什麼、資料怎麼走，以及哪些地方尚未接通。主要交付是對話中的說明；有需要才保存為使用者文件。

這符合本集合「使用者不需要工程詞彙也能得到負責任的工程行為」的目標。既有 `architecture-context` 明確排除一般 repository 熟悉工作，負責的是找回與維護非顯而易見的架構意圖；兩者的使用者與完成條件不同。前者要讓人理解目前產品，後者要讓後續變更保留重要理由與邊界。[集合理念](philosophy.md)、[architecture-context](../skills/architecture-context/SKILL.md)

以下流程與評估案例是根據來源及本 repo 邊界推導出的設計建議，並非 C4 或 arc42 規定的 agent 工作流程。

## 研究依據

| 第一手來源 | 對本需求的啟發 |
| --- | --- |

| [C4：Dynamic diagram](https://c4model.com/diagrams/dynamic) | 複雜互動可用有順序的圖輔助說明特定功能；不需要替每個功能都畫圖。 |

## 建議流程

### 參考 ask-matt 的流程定位

使用者提供的 [ask-matt](/Users/ray.shao/.codex/skills/ask-matt/SKILL.md) 是依使用情境選擇 skill 的路由器。它把研究、設計討論、架構改善候選盤點與實作分開，並指出研究是提供思考材料。這裡借用這種分工：`explain-project` 作為「已有專案，先看懂現況」的獨立入口；解說完成後，使用者若想查故障、討論改法或救援，再進入相應流程。

`ask-matt` 本身沒有提供從程式追蹤資料流並向人解說的完整步驟，因此它適合做流程定位參考；實際導覽方法仍需由入口、呼叫關係與資料讀寫的證據建立。這項提案不沿用它整套 issue tracker 設定、規格拆票、TDD 或跨 session 流程，也不把理解現況自動轉成建置任務。

1. **定位目前版本。** 確認 checkout、工作區變更、應用程式與執行入口。對開發中的 repo，以目前可讀取的工作區為準，不能只看已提交版本。需要遵守的 repository 指令仍須讀取；`AGENTS.md`／`CLAUDE.md` 是工作規則與設計線索，不是要交給使用者閱讀的成品，也不能取代實作證據。
2. **先建立全貌。** 讀 workspace／套件設定、主要入口與路由、服務啟動位置、資料 schema 和對外 client，辨識產品、後台、worker、資料儲存及外部服務。套件存在只算線索，要找到實際接線才能宣稱正在使用。
3. **從使用者動作追資料。** 選一到三個涵蓋不同重要邊界的代表流程：例如看列表、送出資料、等待背景工作。沿著入口追到事件處理、API／服務、驗證與權限、資料讀寫、回應與畫面更新。只描述實際存在的步驟；純前端、CLI、資料管線都不應被硬套成前後端三層。
4. **查清關鍵資料歸誰管。** 說明資料來自哪裡、在哪裡轉換、什麼地方負責最後判定、存在哪裡、刷新後是否保留、什麼情況會送到外部。清楚區分畫面暫存、快取與正式儲存。
5. **查出進度與斷點。** 對照 callers、路由註冊、啟動設定、feature flag、mock adapter 與測試，辨識目前接線。必要時讀架構紀錄理解原意；兩者不同時分開說明，不在導覽途中自行同步文件或修程式。
6. **分層說明。** 先用一小段白話總覽，再說主要責任與代表資料流，最後指出未完成處及本次未涵蓋區域。關鍵結論附少量可點的程式位置，讓使用者可追問，但不要求逐檔閱讀。

閱讀過程維持唯讀。不要因為發現缺口而啟動救援、重構、補文件、安裝套件或資料遷移。可以利用既有且可安全唯讀觀察的執行環境補充證據；若驗證需要變更環境或造成外部副作用，先確認該操作在授權範圍內。無法啟動時仍能交付有界線的靜態解說。

## 快速與整體涵蓋的取捨

「整個架構」先指主要應用、責任、儲存與外部邊界的全貌，不承諾讀完每個檔案。第一輪先涵蓋所有主要執行單元，再深入代表流程；如果其他流程重複已知接線，就先摘要，不持續展開。對 monorepo，不能只讀第一個 web app 就宣稱涵蓋全 repo。

用可見的停止條件控制成本：主要責任可描述、代表流程可追到輸入與輸出、關鍵儲存與外部邊界已識別、未讀與未驗證部分已列明，即可交付第一版。對未知邊界或使用者指定流程再深入。這是漸進式閱讀的設計選擇，尚無實測依據可承諾固定分鐘數或完整度百分比。

## 把接線狀態與驗證證據分開

不能把「程式存在」「真的連上」「本次跑過」混為一談。建議採兩個維度，用自然句子呈現即可，不必每個段落都標籤：

| 維度 | 可用描述 |
| --- | --- |
| 實作／接線 | 現有入口可追到實作；目前走假資料；程式存在但未找到入口接線；只有文件中的規劃；證據不足。 |
| 執行證據 | 本次在明確環境觀察到；僅有既有測試或紀錄支持；由靜態程式推導，本次未執行。 |

例如：「儲存按鈕目前會呼叫後端，再寫入資料庫；這條路徑可從程式追到，但本次沒有連線執行。」不能改寫成「儲存功能已驗證正常」。若沒有找到 caller，只能說「在已查閱範圍未找到」，除非已排除框架自動路由、動態註冊等入口，才可進一步判定未接線。

資料 schema／migration 只能證明 repo 描述的資料設計，不能單憑它宣稱正式環境已套用；文件寫的部署方式也不能證明目前部署狀態。

## 預期使用者會看到什麼

以下是虛構例子，示範說明形式，並非對本 repo 的程式判斷：

> 這個產品幫你整理待辦。畫面負責輸入與顯示，伺服器負責確認誰能修改，資料庫負責長期保存。
>
> 你按下「新增」後，內容先送到伺服器，確認登入者與內容後才存入資料庫；成功回覆後，列表顯示新項目。輸入框裡尚未送出的文字只留在畫面中，刷新就會消失。
>
> 提醒設定目前仍使用範例資料，尚未看到它連到背景通知工作。新增待辦的接線可由程式追到，本次沒有啟動環境驗證。

若圖有幫助，補一張小圖即可：`使用者 → 畫面 → 伺服器 → 資料庫`，箭頭寫「送出待辦」「檢查後儲存」等具體動作，並標明這是靜態程式推導或實測。正式報告再以實際名稱、證據與存在的邊界替換；不要輸出這張通用圖假裝完成理解。

## 與現有 skill 的邊界

| Skill | 完成條件 |
| --- | --- |
| 建議的 `explain-project` | 使用者能說出產品目的、主要責任、資料流程、現況與不確定處；不要求修改 repo。 |
| `architecture-context` | 非顯而易見的架構意圖可找回；已授權變更時維持紀錄一致。 |
| `rescue-vibe-project` | 先就發現的問題 checklist 達成共識，再修復已選的流程並驗證。 |
| `a2a-handoff` | 另一個 agent 收到可接續任務的精確狀態；不負責一般人類導覽。 |

此區分延續既有 [skill ownership](skill-routing.md) 與 [composition](skill-composition.md) 原則。`explain-project` 可以在證據需要時參考架構意圖，但不用固定呼叫全部 guardrail。只問「帶我看懂」時直接開始閱讀與說明；使用者之後要求修改，再依該任務處理授權與確認，不把導覽隱含轉成實作。

## 建議評估案例

| 情境 | 通過標準 |
| --- | --- |
| `CLAUDE.md` 說使用正式 API，現行入口接 mock | 告知現在走假資料，將文件說法標為意圖或過時線索，不照抄成現況。 |
| DB service 有完整實作，畫面只寫 local state | 追到真正使用路徑，解釋刷新後資料是否消失；不因 service 存在就宣稱保存成功。 |
| 前端、API、worker 並存 | 全貌包含三者；追到代表性的同步與背景流程，指出佇列或事件邊界。 |
| 環境缺少憑證，不能跑 | 完成靜態解說，明示未驗證；不宣稱正式服務可用，也不要求先部署才開始解說。 |
| 沒有 agent 文件的半成品 repo | 從設定、入口、caller、schema 建立說明，不依賴先新增 `AGENTS.md`。 |
| 使用者不懂技術，問資料放哪 | 直接用產品名詞說明儲存位置與生命週期，程式連結只作可選證據。 |
| 工作區含未提交的接線變更 | 描述目前工作區，必要時點出與提交版本不同，不遺漏進行中的變更。 |
| 架構說明中發現缺陷 | 回報現況與影響，不修改檔案、不自行進入 rescue 確認或修復流程。 |
| 動態路由或 plugin 註冊 | 檢查註冊規則後再判斷接線，不能用文字搜尋不到 caller 就定論為死碼。 |

研究階段建議先以純前端 mock 專案及包含 API／背景工作的 repo 試跑。後續實作已完成兩個隔離範例的解說評估，詳見[執行紀錄](../evaluations/explain-project/runs/2026-09-07/README.md)；這仍不等於已透過真人測試證明理解程度或速度有所提升。
